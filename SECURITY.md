# Безопасность Эндотеки

Этот документ описывает, как устроен доступ в системе. Фронтенд **не является** границей авторизации: его проверки нужны только для UX. Решения принимает Postgres (RLS и `SECURITY DEFINER` RPC) и Edge Functions с секретами.

## Принципы

1. Браузер работает только с **anon key** и JWT пользователя. `service_role` недоступен клиенту.
2. Прямые `INSERT` / `UPDATE` / `DELETE` с клиента на таблицы запрещены. Изменения идут через RPC с проверкой `has_permission(...)`.
3. Идентификаторы с фронтенда не считаются достаточным основанием: RPC проверяет существование записи, права и бизнес-правила.
4. Секреты (SMTP, токен бота, service role, cron) живут только в окружении функций и CLI импорта, не в React и не в `app_settings`.
5. Шаблоны документов рендерятся как текст React, без `dangerouslySetInnerHTML`.

## Аутентификация

- Вход: email и пароль через Supabase Auth (`signInWithPassword`).
- Сессия хранится в браузере (`persistSession`), токен обновляется автоматически.
- Проверка сессии на сервере: `auth.getUser()`, не только локальный `getSession()`.
- Неактивный профиль или отсутствие профиля приводит к выходу.
- Выход: `auth.signOut()` после записи аудита.
- Приглашение: Edge Function `invite-user` проверяет JWT и право `users:invite`, затем вызывает `create_invitation` и `auth.admin.inviteUserByEmail`.
- Редирект из письма приглашения разрешён только на `/auth/callback` с origin из `SITE_URL`, URL проекта или localhost.
- Публичная регистрация без приглашения не должна быть включена в Auth. Учётная запись без приглашения создаётся с `is_active = false` и не получает роль.

Первого руководителя создают вручную в SQL после пользователя в Auth:

```sql
update public.profiles set is_active = true where email = 'director@example.ru';
insert into public.user_roles (user_id, role_id)
select p.id, r.id
from public.profiles p
join public.roles r on r.code = 'director'
where p.email = 'director@example.ru';
```

## Авторизация

- Права задаются ролью, не именем роли в интерфейсе.
- `has_permission` учитывает `profiles.is_active`.
- Назначение ролей: только `users:update`; роли `director` и `chief_engineer` назначает только руководитель.
- Нельзя снять роль или отключить последнего руководителя.
- Нельзя отключить собственную учётную запись через RPC.
- Матрицу прав меняет только руководитель (`roles:update` + роль `director`). Право `roles:update` нельзя выдать другой роли; у руководителя нельзя убрать управление доступом.
- Маршруты React (`RequireAuth`, `RequirePermission`) скрывают экраны. Тот же отказ должен происходить в RPC.

## RLS

- RLS включён на рабочих таблицах.
- Типичная политика: `SELECT` для `authenticated` при наличии права на чтение.
- Запись через политики клиента снята (revoke insert/update/delete). Исключения исторически закрываются RPC.
- Настройки `app_settings`: полный просмотр только при `settings:read`; ключи `order_number` и `deadline` доступны при работе с заказами.
- Журнал аудита: чтение через `list_audit_events` при `audit:read`; изменение и удаление строк запрещены триггером.
- Импорт (`import_*`): доступен `service_role`, не `authenticated`.

## Бизнес-правила

- Смена статуса заказа: только активный переход из справочника и право, указанное на переходе. Клиентский UUID статуса без перехода отклоняется.
- Склад и FIFO: списание считает сервер по дате партии. Клиент не передаёт batch id.
- Продажа подтверждается RPC: черновик, остаток, затем FIFO и фиксация.
- Корректировки и инвентаризация — отдельные RPC с `inventory:*`.
- Шаблоны документов: правка при `documents:edit_templates`; системный шаблон нельзя удалить.

## Файлы (Storage)

- Бакет `order-attachments` приватный, лимит 10 МБ, типы JPEG/PNG/WebP/PDF.
- Загрузка: путь `{order_id}/{файл}`, одна папка, UUID заказа.
- Регистрация файла в БД проверяет путь, MIME и размер.
- Чтение объекта возможно, только если есть строка в `order_attachments` и право `orders:read`.
- Ссылки на вложения: только `http://` или `https://`, без логина в URL.

## Шаблоны и XSS

- Плейсхолдеры `{{key}}` подставляются в текстовые узлы.
- Неизвестные ключи отбрасываются.
- Картинки шаблона принимаются только по http(s) без credentials.
- QR строится как data-URL на клиенте, не как HTML из шаблона.

## Секреты

| Секрет | Где хранить | Где нельзя |
| --- | --- | --- |
| `VITE_SUPABASE_ANON_KEY` | `.env` фронтенда | считать его приватным: он попадает в бандл |
| `SUPABASE_SERVICE_ROLE_KEY` | Edge Functions, CLI импорта | `VITE_*`, репозиторий, `app_settings` |
| `SMTP_PASSWORD` | секреты `dispatch-notifications` | форма настроек |
| `TELEGRAM_BOT_TOKEN` | секреты функций | форма настроек |
| `TELEGRAM_WEBHOOK_SECRET` | секреты `telegram-webhook` (обязателен) | клиент |
| `CRON_SECRET` | cron и функции `process-deadlines`, `dispatch-notifications` | клиент |

Файл `.env` в git не коммитится. В репозитории только `.env.example`.

## Журналирование

- Аудит пишется RPC `record_audit` / `record_auth_event`. Клиент не вставляет строки в `audit_events`.
- С клиента разрешены только события входа, выхода и смены пароля.
- В консоль не пишутся пароли, токены и сырые объекты ошибок Auth.

## Резервные копии и поставка

- Резервные копии: штатные backup проекта Supabase (ежедневно) плюс выгрузка перед миграциями.
- Миграции только через цепочку `supabase/migrations`, от роли владельца.
- Edge Functions деплоить с секретами окружения, не с хардкодом.
- В Auth: отключить публичный signup, включить подтверждение приглашения.
- Cron: заголовок `Authorization: Bearer <CRON_SECRET>` или service role длиной не менее 20 символов. Пустой ключ не считается валидным.
- Telegram webhook без `TELEGRAM_WEBHOOK_SECRET` отклоняет запросы.
- После инцидента: отозвать ключи в Dashboard, прокрутить пароли SMTP/бота, проверить `audit_events`.
