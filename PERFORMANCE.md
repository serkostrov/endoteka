# Производительность Эндотеки

Этот документ фиксирует решения, которые уже приняты. Не ускорять «на всякий случай»: виртуализация, `useMemo`/`useCallback` и новые индексы имеют смысл только при измеренной проблеме.

## Что грузит браузер

Списки с потенциально тысячами строк идут **страницами с сервера** (обычно 20 записей) и **фильтруются в запросе**, а не в памяти.

| Экран | Пагинация | Поиск |
| --- | --- | --- |
| Заказы, клиенты, задачи, склад, продажи, документы, журнал | да | debounce 300 мс |
| Приборы, сотрудники | да | debounce 300 мс |
| Уведомления в шапке | лимит 30 | нет таблицы |
| Шаблоны документов | нет | мало записей, отдельный RPC |

`placeholderData: keepPreviousData` на списках убирает мигание пустой таблицы при смене страницы и фильтра.

Справочники сотрудников для выпадающих списков (`list_active_employees`) остаются целиком: это штат сервиса, не операционные таблицы.

## Бандл

Страницы после входа грузятся через `React.lazy` (`src/lib/lazy-page.ts`). Вход, callback сессии, установка пароля и 404 остаются в основном чанке — это короткий путь без рабочего стола.

`Outlet` обёрнут в `Suspense` в `AppLayout` / `AuthLayout`.

`useMemo` / `useCallback` специально не добавлялись: лишние списки убраны пагинацией, а не мемоизацией ячеек.

## Склад

- Списание с ранних партий считает `consume_inventory_fifo`: advisory lock на позицию, `FOR UPDATE` партий по `receipt_date, created_at, id`. Клиент не передаёт batch id.
- Остаток в карточке и в списке совпадает с партиями: `remaining_quantity` — кэш, который пишет только триггер журнала. Список склада больше не суммирует всю историю `inventory_movements`.
- Подтверждение продажи: lock + переход `draft → confirmed` с `RETURNING`; повторное подтверждение отклоняется.
- Инвентаризация: advisory lock на документ.
- Повторное нажатие «Списать в заказ» отсекается на клиенте до ответа сервера; гонка двух запросов всё равно сериализуется lock’ом в RPC.

## Заказы

- Номер: `UPDATE order_number_sequence … RETURNING` на одной строке. Параллельное создание не даёт одинаковый номер. Пропуск номера после отката после `next_order_number` допустим.
- Смена статуса и назначение: `SELECT … FOR UPDATE` по заказу, затем проверка перехода и прав. Второй параллельный переход видит уже новый статус и отвергается.
- Повторная отправка формы создания заказа игнорируется, пока мутация в полёте.

## Уведомления

`emit_domain_event` пишет событие, затем обрабатывает его во вложенном блоке `BEGIN/EXCEPTION`. Ошибка доставки не откатывает заказ, списание или продажу. Колокольчик в шапке не тянет всю историю — только последние 30.

## Рабочий стол

`get_operational_dashboard` считает метрики заказов **одним проходом** по открытым заказам (не десятком `count(*)` по `order_list_items` с join приборов). Превью — `limit 5`. Нулевой остаток проверяется по партиям с `remaining_quantity > 0`, без полного join журнала движений.

## Что сознательно не делали

- **Виртуализация таблиц.** При 20 строках на страницу она не нужна.
- **`pg_trgm` / GIN по `ilike %…%`.** Поиск по подстроке станет узким местом только на очень больших таблицах; btree по `lower(name)` этот шаблон не ускоряет.
- **Новые индексы «на всякий случай».** Уже есть индекс партий для списания, уникальный номер заказа, статус / срок / ответственный, задачи, продажи, аудит, непрочитанные уведомления.
- **Смена порядка списания партий или нумерации.** Алгоритм корректности не трогали.
- **`staleTime` / отключение `refetchOnWindowFocus`.** Для операционного экрана 30 с и обновление при фокусе уместны.
- **Ручной `manualChunks` в Vite.** Разрезание маршрутов даёт основной выигрыш; vendor split без измерения не добавляли.
