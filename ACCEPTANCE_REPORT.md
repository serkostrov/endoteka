# Отчёт приёмки Эндотеки

Сверка с исходными доменами ТЗ. Новые требования не добавлялись. Критические ворота: typecheck, lint, production build — после исправлений в этом проходе.

Проверка сценариев — по коду, миграциям и RPC. Живой прогон в браузере в этой сессии не выполнялся.

## Сводка ворот качества

| Ворота | Результат |
| --- | --- |
| Ошибки TypeScript | Нет (прогон `npm run typecheck`) |
| Ошибки ESLint | Нет (прогон `npm run lint`) |
| Production build | Успешен (`npm run build`) |
| Критический RLS | Есть: RLS включён, прямые INSERT/UPDATE/DELETE у `authenticated` отозваны, запись через RPC |
| Секреты во фронтенде | Нет: только `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` |
| Правила только в UI | Нет: статусы, FIFO, номера, серийники, права проверяет Postgres |
| Отрицательный остаток | Невозможен: проверка суммы партий + CHECK `remaining_quantity >= 0` |
| Склад не атомарный | Операции в одной транзакции RPC |
| Дубли серийных номеров | Запрещены: `unique (lower(btrim(serial_number)))` |
| Дубли названий номенклатуры | Запрещены: `unique (lower(btrim(name)))` |
| Коллизия номеров заказов | Предотвращена: `UPDATE … RETURNING` последовательности + unique `orders.number` |
| Правка аудита обычным пользователем | Невозможна: триггер + revoke на таблице |

**Готовность:** критические ворота пройдены. Неполнота, которая остаётся, — операционные настройки (cron, SMTP, Telegram, Auth signup) и ограничения ролей, а не дыры в инвариантах.

## Критические сценарии

### Сценарий 1 — заказ от приёма до выдачи

**Статус: выполним** на роли `director` (или `chief_engineer` + кладовщик на списание).

Цепочка статусов по умолчанию: `received → diagnostics → waiting_approval → repair → quality_check → ready → issued`. Заключение обязательно для перехода на согласование (RPC). Гарантия создаётся при выдаче.

| Шаг | Код |
| --- | --- |
| Клиент / прибор / история серийника | `CustomerPicker`, `search_device_serial` |
| Создание заказа и номер | `create_order`, `next_order_number` |
| Назначение | `update_order` + запись журнала |
| Диагностика | `save_order_diagnostics` |
| Списание | `consume_inventory_for_order` + FIFO + журнал |
| Выдача | `change_order_status` + `device_warranties` |

**Ограничение:** у менеджера нет `diagnostics:update` — один менеджер сценарий не закрывает. Это матрица ролей, не баг UI. Правило «ответственный назначен» в код переходов не посеяно: назначение необязательно для смены статуса.

### Сценарий 2 — приход → ремонт FIFO → история

**Статус: выполним.** `receive_inventory` увеличивает остаток; списание в заказ идёт FIFO; в карточке позиции тип «Израсходован в ремонт» и номер заказа; в журнале заказа появляется списание.

### Сценарий 3 — продажа FIFO → документ → история

**Статус: выполним.** `confirm_sale` списывает FIFO; тип движения «Продан»; вкладка документов на счёте (накладная из шаблона) плюс печать черновика.

### Сценарий 4 — приглашение и запрет чужих операций

**Статус: выполним** при задеплоенном `invite-user` и отключённом public signup. Роль ставит триггер `handle_new_user`. Обход UI на мутациях режется RPC/`has_permission`.

### Сценарий 5 — динамическое поле диагностики

**Статус: выполним.** Новое активное поле появляется в протоколе после refetch. Валидация на клиенте и в `validate_dynamic_field_value` / `save_dynamic_field_values`.

### Сценарий 6 — срок → уведомление → email/Telegram

**Статус: выполним при ops.** Cron `process-deadlines` + `dispatch-notifications`. По умолчанию in-app ответственному. Email/Telegram — если включены канал и маршрут. Кнопка «Проверить сроки» снова вызывает RPC с проверкой `settings:update` (регрессия revoke исправлена).

## Исправления этого прохода

1. Журнал заказа: списание запчастей и смена ответственного.
2. Системная этикетка запчасти: штрихкод `{{item.barcode}}`.
3. `process_order_deadline_notifications` снова доступен `authenticated` (проверка права в RPC).
4. `consume_inventory_for_sale` отозван у клиента (актуальный путь — модуль продаж).
5. Вкладка документов на продаже.
6. README: все edge-функции, cron, Auth, импорт.

Миграция: `supabase/migrations/20260826900000_acceptance_fixes.sql`.

## Что не меняли (не выдумывать ТЗ)

- Матрицу ролей (менеджер без записи диагностики).
- Уникальность ИНН клиента.
- Уникальность штрихкода номенклатуры.
- Обязательность ответственного на переходах.
- Виртуализацию таблиц и Realtime для колокольчика.
